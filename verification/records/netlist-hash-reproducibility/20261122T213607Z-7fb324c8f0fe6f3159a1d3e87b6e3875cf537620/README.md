# netlist_sha256 cross-build reproducibility (issue #32)

**Finding: cosmetic text.** The two committed flow-smoke records' different
`netlist_sha256` values are fully explained by the `/* Generated by Yosys … */`
banner comment on the netlist's first line, which names the compiler that
built Yosys. The netlist content is byte-identical across the two Yosys
builds; nothing else in the file differs. Same-build synthesis is
deterministic (two runs on one host: byte-identical netlists).

This record closes the question the issue posed: `netlist_sha256` cannot by
itself distinguish "the design changed" from "the Yosys build changed" — but
a banner-normalised hash can, and the flow-smoke runner now records one next
to the raw hash (see "Disposition" below).

## Evidence chain

All commands and outputs: `measurements.txt` in this directory. The two
netlists are kept here as evidence (`smoke_synth.v` as measured on this
host, `smoke_synth.clang-banner.v` the banner-rewritten variant), because
`flow/build/` is gitignored and the committed records alone did not include
them.

1. **Same-build determinism** — `klt synthesize` run twice on this host
   (fresh `flow/build/` each time): the two netlists are byte-identical
   (empty `diff`), both `103e9ce5…c02d`.
2. **This host reproduces committed run 1 exactly** — this host's Yosys
   provenance string is the same GNU `/usr/bin/c++ 13.3.0` build as record
   `../flow-smoke/20261122T200938Z-53870c0e3c0d6ddc1e615b047c574be22e7f8441/`,
   and the fresh netlist's sha256 equals that record's committed
   `netlist_sha256` (`103e9ce5…c02d`).
3. **The banner is the only build-dependent text** — `grep` over the netlist
   finds the build string only on line 1, the `/* Generated by Yosys … */`
   comment Yosys writes into its Verilog output.
4. **Banner rewrite reproduces committed run 2 exactly** — rewriting only
   that line's build string to the Clang `/usr/bin/c++ 18.1.3` string
   recorded in run 2's `provenance.json`
   (`../flow-smoke/20261122T205746Z-521083ad66e0bb20d8e8d5c5bdcef941cba70df4/`)
   yields sha256 `7cba8f62…8445` — equal to run 2's committed
   `netlist_sha256`. By collision resistance, run 2's netlist was
   byte-identical to run 1's except for the banner line; the complete
   cross-build diff is that one comment.

## What was and was not measured

- Measured: same-build determinism (two runs, one host); cross-build netlist
  equality modulo the banner (via exact reproduction of **both** committed
  hashes,GNU- and Clang-banner variants, from one measured netlist).
- Not measured: a second Yosys binary at `PIN_YOSYS`/`PIN_YOSYS_SHA` actually
  executing synthesis. It was not needed: reproducing both committed hashes
  by banner substitution alone pins the entire cross-build difference to the
  banner. A second build could only add differences beyond the banner, which
  the committed hashes (both reproduced here) rule out for these two runs.

## Classification (per the issue's three options)

**Cosmetic text (banner/comment).** Not a name/ordering difference, not a
hash from elsewhere, and not a synthesis non-determinism.

## Disposition

`verification/tools/run_flow_smoke.py` now logs, right after the synthesize
stage, the pairing `netlist_sha256=<raw> netlist_sha256_banner_normalised=<n>
(yosys build: <full build string>)`, so future record comparisons are well
defined: equal normalised hashes across records with different
`tool_versions.yosys` build strings mean the netlist content is identical
and only the Yosys build differs. The raw hash is unchanged (klt emits it;
envelopes stay verbatim).

klayout-tools friction filed upstream: klt's synthesize envelope records
`netlist_sha256` over the banner verbatim, so the field is
build-sensitive — 2AMLogic/klayout-tools#7277.

No spec value or design claim is touched by this record.
